# Outreach and send safeguards Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship spec phase 3: an outreach workflow and a reply-triage loop for @sales, plus the sending safeguards they need (a daily send cap per connected account, a pace between browser sends, and no send on its own from a loop or a workflow step).

**Architecture:** Two safety pieces in code, then markdown on top. App sends get a per-account daily cap, counted in `team/approvals.json` rows under `approvals.LOCK` the way browser sends already count against a site's daily cap. Browser sends get a minimum gap per site, checked in the same `approvals.claim_send` call as the cap. A job run or a workflow step holds every send, even on a "Sends without asking" grant, so approving a plan never approves what is inside it. Then two @sales skills (`outreach-draft`, `reply-triage`), one workflow (`outreach`) and one loop template (`reply-watch`).

**Tech Stack:** Python 3 standard library, `unittest`, vanilla JS dashboard, Markdown skill files, `python -m evals` (offline and `--live`).

**Spec:** `docs/superpowers/specs/2026-11-21-skills-workflows-loops-design.md` ("Safety", "Loop rules", "Phases" item 3, "Open items": outreach results). Plan 6; phase 2 was plan 5 (`2026-11-23-skills-and-domain-bots.md`).

## Global Constraints

- Public repo: fixtures and examples use `acme`, `demo`, `profile-a`, `profile-b` only. `python3 -m unittest tests.test_no_usage_data` before every commit.
- Plan approval is inert. Each send, spend or delete inside a plan keeps its own approval, per action.
- Sending loops add a daily send cap per account and throttling of browser actions.
- Loops never send, spend or delete on their own. New loops start in report mode.
- Skill standard (`tests/test_skill_standard.py`): frontmatter `name` and `description`, reads `intake`, a `Recommendation`, a `## Write gate`, 35 to 130 lines, under the 4500-character cap.
- Workflow standard: `## Steps` lines `N. skill: x | bot: y | output: ... | gate: no|approval [| checker: z]`, plus `## Stop when` and `## Always ask first`.
- Loop template standard: the 13 parts in `core/loop_templates.PARTS`, report mode, 3-try cap in State. A quiet run "ends this run (the loop keeps going)", never "stop".
- A bot card lists 3 to 6 skills. @sales goes from 4 to 6. No other card grows.
- Outreach results have no metric source: the owner adds them by hand as evidence entries (`add-evidence`).

## Decisions

- **What counts as a send (apps):** `app_rules.is_send(slug, toolkit)`: a non-read whose action words (after the toolkit prefix) include one of `SEND REPLY FORWARD PUBLISH BROADCAST NOTIFY COMMENT TWEET DM`, or `POST` anywhere when the first word is not a read verb. Drafts (`GMAIL_CREATE_EMAIL_DRAFT`) are not sends; `GMAIL_SEND_DRAFT` is. When unsure the rule counts it: a false send only uses up cap.
- **Cap per account:** `integrations.json` key `send_caps.<account id>` = int 1 to 500. Unset reads as `DEFAULT_SEND_CAP = 50`. Counted across every bot and workspace for 24 hours from each send's start. Applies to sends on their own (act grant) and to Approve clicks. An Approve over the cap leaves the card pending with the reason.
- **Browser pace:** `browser.json` site row gains `gap` (seconds between sends on that site, 0 to 3600). Unlisted sites and rows without one use `DEFAULT_GAP = 30`. Defaults: `linkedin.com` 120, `instagram.com` 180. When the next send is due within `MAX_WAIT = 120` seconds the relay waits, then sends; later than that it refuses with the time it is due. Only sends are paced: reads and navigation are not.
- **Held in loops and workflows:** a job run (any mode) or a workflow step turn holds every app send (`is_send`) as a card even on an act grant, and needs an approved send plan for every browser send even on an `act` browser level. Other act writes (a calendar event) keep running on their own.
- **Loop template name:** `reply-watch` (the skill it loads is `reply-triage`; one name per file).

## Review Focus

- An owner who approves step 3 of `/outreach` (the plan) sees every message still waiting as its own card, and nothing went out. Test: Task 3, `test_workflow_step_holds_sends_on_act_grant`.
- An account at its cap on a busy day: the 51st act send is refused with a line naming the account and the limit, and the 51st Approve click keeps the card pending. Test: Task 1, `test_act_send_over_cap_refused`, `test_approve_over_cap_stays_pending`.
- Two workspaces sending from the same Gmail account share one cap (it is the account that gets flagged, not the workspace). Test: Task 1, `test_cap_counts_across_workspaces`.
- A bot sending 10 LinkedIn messages in one turn: sends go out 120 seconds apart, the turn is not killed by the idle watchdog while it waits, and a send due later than 120 seconds is refused with its time. Test: Task 2, `test_send_inside_gap_waits_then_sends`, `test_send_far_inside_gap_refused`; the watchdog check is in Task 4.
- A reply that says "unsubscribe" or "stop" marks the row do-not-contact and gets no drafted answer. Test: Task 3 live case `skill-reply-triage-optout`.
