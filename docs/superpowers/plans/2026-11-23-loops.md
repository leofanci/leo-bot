# Loops Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Scheduled jobs become loops. They can pass work along bot chains. They start in Report only, stop on their own stated condition or at an expiry date, and can wake on changes in Leo Bot's own data. A loop can offer the owner a workflow to start. The owner manages every loop on one screen, and each workspace may set its own chain limits.

**Architecture:**
- A loop is the existing scheduled job (`core/jobs.py`) with three new fields:
  - `stop`: the stop condition, as text.
  - `expires`: an epoch time, or None.
  - An optional own-data `check`.
- The job runner pauses a loop when it expires.
- The ask path stops refusing a job's handoff. It also reads two marker lines in a job's reply:
  - `LOOP DONE: <why>` turns the loop off.
  - `START: /<workflow> <brief>` becomes a button in the thread for the owner.
- Each workspace's chain limits live in `team/chain.json`. `core/chain.limits(ws)` reads that file first, then Settings.
- The Team screen's job list moves to a Loops screen with edit, renew and cost.

**Tech Stack:** Python 3 standard library, `unittest`, vanilla JS in `dashboard/app.js`.

**Spec:** `docs/superpowers/specs/2026-11-21-skills-workflows-loops-design.md`. The plan covers these sections:
- "Loop rules"
- "Loops and bot chains"
- "Loop wake-ups"
- "Loop defaults and management"
- "Bots passing work to each other" (the per-workspace override only)

This is plan 3 of 4. Plan 4 covers library content: `loop-design`, loop templates, the weekly review and signal-sweep loops, and the per-item attempt cap written into loop skills.

## Global Constraints

- Tests run with `python3 -m unittest discover -t . -s tests`. Run `python3 -m unittest tests.test_no_usage_data` before every commit.
- Public repo: fixtures use only `acme` and the shipped bot ids. No real names and no user quotes in tracked files.
- A loop never raises its own mode or cap. A loop's own run proposes no jobs; that rule is already in place and stays. Only the owner promotes a loop, on the Loops screen or by accepting a proposal in their private thread, which comes with Undo.
- A chain started by a loop runs inside the loop's mode:
  - Report only saves nothing.
  - Approval waits on every save.
  - App writes always wait.
  - The loop's daily cap counts every hop.
- A loop never starts a workflow run itself. It can only offer a Start button that the owner clicks.
- Defaults:
  - A new loop's mode is `loop_mode` in Settings, General. It defaults to `report`.
  - Expiry is `loop_days`. It defaults to 30, and 0 means it never expires.
  - Jobs saved before this plan keep their mode and never expire. Nothing migrates.
- The commit messages carry no co-author trailer. Work on branch `feat/loops` in the main checkout, then PR, CI, merge.

**Not in this plan:**
- The daily send cap for sending loops (spec phase 3).
- Loop template content (plan 4).

## Review Focus

- A job hop runs on the hop bot's own engine. An unmetered engine refuses the hop with the same `JOB_UNMETERED` line, and the run never spends unmetered money.
- `LOOP DONE:` inside a consulted teammate's answer must not stop the loop. Only the job's own bot's final reply counts.
- `START:` naming an unknown workflow, or a workflow whose bots are off, shows no button. Instead it shows a notice naming the problem.
- An expired loop that the owner renews runs at its next due time. It does not run at once for every slot it missed.
- An own-data check on a list or project the job's workspace cannot see is refused when the job is proposed, and again when it runs.
